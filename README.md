# LifeMate

> **Agentic AI that turns Vietnamese voice requests into real actions.**

This repository contains a solution for the **LifeMate**.

## 1. Context

LifeMate is a voice-driven, tool-using AI agent. The goal is not simply to transcribe speech or answer a question. Given a spoken Vietnamese request, the user's context, conversation history, and the applications available on the device, the agent must determine what the user wants and execute the appropriate actions through the tools exposed by those applications.

A successful agent should complete everyday tasks across connected services—for example, controlling smart-home devices, transferring money, booking a ride, ordering food, sending email, or creating reminders. A single request may require several dependent actions across multiple applications.

The system is evaluated primarily on **the actions it performs and the resulting application state**, rather than on the fluency or length of its natural-language response.

## 2. Problem definition

### Inputs

For each sample, the agent may receive:

1. **Audio request** — the user's latest spoken request, primarily in Vietnamese and possibly mixed with common English words.
2. **User context** — current date/time, timezone, location, and profile information such as home or work addresses.
3. **Available applications and tools** — connected services (such as smart home, banking, ride-hailing, food delivery, and email). Each tool is described by a JSON schema defining its name, parameters, and expected argument types.
4. **Conversation history** — earlier turns in the same conversation, when available. The latest audio should be interpreted in the context of those turns.
5. **Simulated application environment** — the state of the user's devices, accounts, contacts, reminders, and other app data. The agent interacts with this environment through the provided tools.

### Required output

The agent produces an **ordered list of tool calls**, together with the sample ID and a final environment state hash. Each call contains a tool name and its arguments.

The agent has three possible outcomes:

- **Execute the request:** call the required tools in the correct order, using arguments consistent with the tool schemas and available context.
- **Ask for missing information:** call `sys.ask_missing_info` when required information is not available. The clarification request must identify the intended tool and the missing parameters. This can happen after other valid actions have already been completed.
- **Handle an unsupported request:** return an empty `tool_calls` list (`[]`) when none of the installed applications can perform the requested task. Do not invent capabilities or call unrelated tools.

The output also includes `state_hash`, generated by the execution environment using `env.get_state_hash()`. This hash is used to verify the resulting application state.

Submissions are represented as JSON Lines: one JSON object per sample, typically written to `submission.jsonl`.

## 3. Core capabilities to build

The solution should address the complete voice-to-action workflow:

- **Vietnamese speech understanding:** handle natural spoken language, colloquial wording, disfluencies, common English insertions, and different regional accents. The challenge data includes synthetic and real voices from Northern, Central, and Southern Vietnam.
- **Context-aware interpretation:** combine the current request with conversation history, time, timezone, location, and user profile information. Resolve references such as “nhà tôi”, “chỗ làm”, “ngày mai”, or “lúc đó” using the supplied context rather than unsupported assumptions.
- **Tool selection:** identify the relevant installed application and choose only tools that are actually available in the sample.
- **Argument generation:** produce schema-valid arguments, using the correct identifiers and values obtained from context or previous tool results.
- **Multi-step planning and execution:** order calls according to their dependencies. For example, retrieve a device list before changing a particular device when its ID is not yet known.
- **Missing-information handling:** ask for clarification when a required value cannot safely be inferred.
- **Out-of-scope handling:** perform no action when no installed application can satisfy the request.
- **State verification:** compute the final hash using the official environment interface and emit the required submission format.


## 4. Engineering principles

1. **Tools are the source of truth.** Use the tool schemas and tool results provided for the current sample. Never fabricate tool names, parameters, device IDs, contacts, account details, or execution results.
2. **Respect the simulated environment boundary.** Read and modify application state through the provided tool interface. Do not bypass the tools by directly inspecting or editing the simulated app data.
3. **Preserve action order.** Execute prerequisite reads before dependent writes, and use results returned by earlier calls to construct later arguments.
4. **Do not guess critical details.** If a required parameter is missing and cannot be resolved from the supplied context or tool results, ask for it using `sys.ask_missing_info`.
5. **Do not over-act.** Execute only actions needed to fulfill the user's request. For unsupported requests, return an empty call list.
6. **Keep output deterministic and valid.** Follow the official output schema, include the required calls and sample ID, and obtain the state hash from the matching environment instance.
7. **Optimize for task completion.** A plausible transcript or a convincing textual explanation is not enough; the target is the correct final state in the simulated applications.

## 5. Data and evaluation considerations

The project is based on everyday Vietnamese digital-life scenarios, including smart-home control, banking, ride-hailing, food delivery, and email. Requests are expressed through both synthetic and real speech and cover regional pronunciation differences.

Evaluation should therefore test more than transcription quality. It should measure whether the system:

- understands the user's intended task;
- selects the correct available tools;
- supplies valid and contextually correct arguments;
- performs all required actions in the correct order;
- asks for missing information when necessary;
- avoids actions for unsupported requests; and
- leaves the simulated environment in the expected state.
